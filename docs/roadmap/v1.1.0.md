## 1. 版本目标

打造 **「智能衣橱体验优化版」**：在不推翻 v1.0.0 架构的前提下，重点打通打卡与添衣闭环、降低录入门槛、堵住打卡数据误覆盖、校正订单日期与穿着统计口径，让日常使用更顺、数据更可信。

一句话：**少打断、少重选、少误判；AI 能认就认，认不了也能填；当天打卡不被静默覆盖。**

---

## 2. 用户痛点

基于 v1.0.0 实际行为与已知限制归纳：

| 痛点 | 现状（基线） | 影响 |
|------|----------------|------|
| 打卡链路断裂 | 打卡中跳转「添加衣物」后，返回路径弱；新衣不一定回到当前勾选列表 | 用户反复退出、重选已勾选衣物 |
| 添衣入口分裂 | 「AI 订单截图」与「手动录入」分按钮，用户需预先判断 | 决策成本高；失败时需重走流程 |
| 当天打卡被覆盖 | 「今日穿搭推荐」等路径可写入同日打卡，易静默覆盖已有记录 | 心情/穿搭记录丢失风险 |
| 订单年份不准 | 淘宝截图常只显示「月-日」；解析补年逻辑需更明确、可测 | 购入日期错误 → 分析区间失真 |
| 统计误伤新衣 | 穿着 TOP / 闲置口径可能把「从未穿过的新衣」当成闲置 | 用户不信任分析页 |
| 打卡识衣仍占位 | 有照片时匹配为随机 UI（属更大后续项，本版以流程体验为主） | 预期管理：本版不承诺真实识衣 |

## 3. 功能列表

### 3.1 打卡流程优化

- 优化「今日穿搭打卡」主路径，减少多余步骤与重复选择
- 支持在打卡过程中添加缺失衣物后，**自动返回当前打卡流程**（保留已选、步骤、临时照片等会话状态）
- 新添加成功的衣物 **自动加入当前已选择列表**
- 提供明确选择：**继续添加** / **完成打卡**（或等价文案），避免模糊返回
- 避免用户为补一件衣服而反复退出并重新勾选

### 3.2 添加衣物流程优化

- **合并** AI 添加与手动添加入口为统一「添加衣物」体验
- 用户主路径：**只上传图片**（订单截图或单品图均可）
- 系统 **优先尝试 AI 识别**（沿用现有 Worker `/ai/vision`，不引入用户填 Key）
- AI 失败或不可用时 **自动降级为手动填写**，并尽量保留已上传图片
- （可选体验）识别中展示明确进度；失败原因用简短 toast/文案说明

### 3.3 打卡数据安全

- 修复「今日穿搭推荐」等写入逻辑 **覆盖当天已有打卡** 的问题
- 若当天已有穿搭/心情等相关记录：提示用户 **替换** 或 **新增**（具体文案与是否允许同日多条，以实现时与现有 `checkins` 模型对齐）
- 无用户确认前，不得静默覆盖已有当天记录

### 3.4 AI 订单识别优化（日期）

- 修复订单购买日期识别/归一问题
- 规则：
  - 截图 **仅显示月份（及日）**、无明确年份 → 使用 **当前年份** 补全
  - 截图或模型输出 **含明确年份** → **必须使用识别到的年份**，不得强行改成当前年
- 预览表单中日期仍可人工修改；入库前保持现有核对提示

### 3.5 数据分析优化

- 上传/入库新衣物后，**自动刷新**分析统计（或保证返回分析页时数据最新）
- 「穿着 TOP」**只统计有效穿着记录**（以 `logs` 等真实穿着为准，口径需在实现注释中写清）
- **从未穿过**的衣物单独归类为 **「暂无穿着」**
- **不应**把新入库、尚未穿过的衣物误判为「闲置」

## 4. 优先级排序

| 优先级 | 模块 | 理由 |
|--------|------|------|
| **P0** | 打卡数据安全（覆盖问题） | 直接丢数据，信任底线 |
| **P0** | 打卡流程：添加后返回 + 自动勾选 + 继续/完成 | 高频路径，体验断裂明显 |
| **P1** | 添衣入口合并 + AI 优先 + 失败降级 | 降低录入门槛，与 AI 能力一致 |
| **P1** | 订单日期年份规则 | 影响分析与购入统计正确性 |
| **P1** | 分析：有效穿着 / 暂无穿着 / 新衣不进闲置 | 纠正误判，提升分析可信度 |
| **P2** | 分析页自动刷新时机打磨、文案与空态 | 在口径正确后优化体验 |
| **本版不做** | 打卡照片真实 AI 识衣（替换 `simulateMatch`） | 基线已标明属更大版本；可列入后续 roadmap |

建议实施顺序：

```text
P0 打卡安全 → P0 打卡闭环
    → P1 添衣统一入口
    → P1 日期规则 + 分析口径
    → P2 刷新与文案
    → 回归 / 发版
```

## 5. 技术风险评估

| 风险 | 等级 | 说明 | 缓解 |
|------|------|------|------|
| 打卡会话状态丢失 | 中高 | `checkinPendingReturn`、临时照片、已选列表需在「去添衣 → 保存 → 回打卡」全路径保持 | 明确会话字段与清理时机；用用例清单覆盖中断/取消 |
| 同日多条 checkin 模型 | 中 | 现有结构支持多条同日记录的程度需对照 `checkins` 读写；「替换 vs 新增」影响列表与日记 | 先读清现有写入路径（打卡确认 / 推荐 / 心情），再定交互 |
| 合并添衣入口回归 | 中 | AI 订单、多件选择、裁剪会话、手动表单均挂在添加流 | 保留 AI Proxy；失败降级不丢图；回归多件订单与裁剪 |
| 日期规则边界 | 中 | 「仅有月日」vs「有年份」解析分支易漏；跨年订单、海外格式 | 单测/脚本覆盖样例；预览页仍可改 |
| 分析口径变更 | 中 | TOP / 闲置 / 「暂无穿着」定义变化可能让老用户感觉「数字变了」 | 文档写清口径；UI 上区分「闲置」与「暂无穿着」 |
| 新衣刷新时机 | 低中 | 入库后若分析页已挂载，需主动重算或失效缓存 | 入库成功回调 / 切回分析 Tab 时重算 |
| 范围蔓延 | 中 | 易顺手做真实识衣、大改推荐算法 | 严格按本清单；识衣单列后续版本 |

**明确不改（除非验收阻塞）：** Worker AI Proxy 协议、数据库表结构大改、无关 UI 翻新。

## 6. 验收标准

### 6.1 打卡流程

- [ ] 打卡中进入添加衣物，保存成功后回到 **同一打卡流程**（步骤与已选不丢）
- [ ] 新保存的衣物出现在 **当前已选择列表** 且为勾选态
- [ ] 存在明确的 **继续添加** / **完成打卡**（或等价）操作，语义清晰
- [ ] 补一件衣服无需重新挑选此前已选衣物

### 6.2 添加衣物

- [ ] 主入口不再强制用户先选「AI / 手动」两套互斥路径（合并后的统一体验）
- [ ] 上传图片后优先走 AI；成功进入可编辑预览
- [ ] AI 失败时自动进入手动表单，图片仍在
- [ ] 用户仍可不依赖 AI 完成入库（降级路径可用）

### 6.3 打卡数据安全

- [ ] 当天已有打卡时，「今日穿搭推荐」等写入 **不会静默覆盖**
- [ ] 出现 **替换 / 新增**（或产品确认的等价）选择；取消则保持原数据
- [ ] 心情打卡与穿搭打卡并存规则与提示行为符合实现说明（需在发版记录写清）

### 6.4 AI 订单日期

- [ ] 仅月日、无年份 → 补 **当前年**，表单可见可改
- [ ] 含明确年份 → 入库默认使用该年，不被改成当前年
- [ ] 至少覆盖：无年订单、有年订单各 1 组样例（可用 `scripts/` 或手工验收）

### 6.5 数据分析

- [ ] 新衣入库后，分析相关统计在约定时机更新为最新
- [ ] 穿着 TOP 仅基于有效穿着记录
- [ ] 零穿着衣物进入 **「暂无穿着」**，不进入「闲置」误判桶
- [ ] 刚入库未穿过的新衣 **不会** 被标为闲置

### 6.6 回归（基线不回退）

- [ ] AI Proxy 仍无需用户 Key
- [ ] 通用图片裁剪 / 重传可用
- [ ] PWA 安装与安全区无明显回退（真机冒烟）
- [ ] 云端衣物 / 打卡同步仍可用

### 6.7 发版门槛

- [ ] 更新 `docs/versions/v1.1.0.md`（从模板复制）
- [ ] 打 Git tag（名称在发版时确定，建议与产品版对齐策略写清）
- [ ] Vercel Production 验证通过
